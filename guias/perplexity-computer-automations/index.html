Perplexity Computer Automations

Cómo usar tareas recurrentes con memoria entre ejecuciones sin automatizar de más.

PRECIO / DISPONIBILIDAD: Automations está disponible para usuarios de Perplexity Computer. Computer está asociado a planes pagos y consume créditos al ejecutar. Pro cuesta USD 20/mes y Max USD 200/mes; Max incluye asignación mensual de créditos. La cuenta Free estándar no incluye Computer. Esperar un trigger no consume créditos; una ejecución sí.

1. Qué cambió

El 29/09/2026 Perplexity lanzó Automations en Computer. Reemplaza Scheduled Tasks y suma dos ideas clave: disparadores por horario o eventos, y memoria del trabajo anterior. Un run puede comparar con el anterior, recordar pendientes y detectar cuando algo esperado no ocurrió.

2. Cómo funciona

horario o evento → Automation → Computer + fuentes → contexto de runs previos → análisis / acción → revisión humana → resultado + historial

Perplexity confirmó triggers para Slack, Gmail, Outlook, Linear y GitHub, con condiciones para filtrar eventos relevantes.

3. Por qué importa

La oportunidad no es que “haga todo solo”. Es sacar de la memoria humana trabajos que hoy se caen por olvido: seguimiento de leads, pricing de competencia, decisiones pendientes, reportes, deploys o cambios que alguien debería revisar cada cierto tiempo.

4. Para quién sirve / para quién no

Sí

Ventas, operaciones, soporte, producto, ingeniería y research cuando cada revisión necesita contexto y criterio.

No

Acciones críticas totalmente autónomas desde el día uno, o flujos deterministas que un cron, Make, Zapier o una API resuelven más simple.

5. Casos prácticos

  • Competencia: cada lunes revisar precios, comparar con el run anterior y marcar sólo cambios materiales.
  • Ventas: detectar cuentas prioritarias sin respuesta durante cuatro días y preparar seguimiento.
  • Ingeniería: al mover un issue a ready, revisar contexto y preparar un cambio para revisión.
  • Operaciones: revisar pendientes abiertos y cerrar sólo los que tengan evidencia.

7. Prompt base

OBJETIVO: cada [frecuencia/evento], [resultado].
FUENTES: [Gmail/Slack/Linear/GitHub/archivos].
Compará con el run anterior y destacá sólo cambios materiales.
Mantené una lista de pendientes y cerralos sólo con evidencia.
Podés leer, analizar y preparar borradores.
Pedí aprobación antes de enviar, publicar, borrar o modificar datos.
Salida:
1. qué cambió,
2. qué sigue pendiente,
3. qué requiere mi decisión,
4. evidencia y enlaces.

8. Implementación exacta

  1. Elegí un proceso que ya hacés manualmente todas las semanas.
  2. Definí un solo resultado medible.
  3. Conectá sólo las fuentes necesarias.
  4. Arrancá read-only o draft-only.
  5. Configurá un trigger específico, no uno demasiado amplio.
  6. Revisá los primeros 5–10 runs.
  7. Medí falsos positivos, correcciones y créditos.
  8. Recién después habilitá acciones adicionales.

9. Precio y costo real

Perplexity usa créditos para Computer y el consumo depende de complejidad, herramientas y duración. Yo pondría un presupuesto mensual por Automation y mediría costo por seguimiento útil, no créditos aislados.

10. Limitaciones y gotchas

  • Los conectores determinan qué puede hacer realmente cada Automation.
  • Una memoria equivocada puede arrastrar supuestos: pedí evidencia y estados explícitos.
  • Triggers amplios pueden generar ruido y gasto innecesario.
  • No gasta créditos mientras espera un trigger, pero sí al ejecutar.
  • Revisá permisos de conectores a nivel admin.
  • No reemplaza una integración determinista cuando una API resuelve mejor el flujo.

11. Comparativa

Make/Zapier: mejores para lógica predecible y APIs. Automations: mejor cuando cada run necesita leer contexto y decidir. Agent API: mejor cuando querés construir el agente dentro de tu propio producto.

12. Qué haría yo

Empezaría por una vigilancia que hoy se cae por olvido: competencia, leads sin respuesta o deploys pendientes. Le daría permiso de leer y avisar, no de ejecutar. Si demuestra precisión durante una semana, agregaría borradores o acciones aprobables.

13. Checklist

  • Objetivo medible
  • Trigger específico
  • Fuentes mínimas
  • Permisos read-only al inicio
  • Presupuesto mensual
  • Aprobaciones
  • Historial de runs
  • Prueba de 5–10 ejecuciones
