Cursor ya no termina en el PR.
Ahora mira deploy y seguridad.

Guía para entender Rollouts + Security Review sin vender humo: qué hacen, cómo los probaría yo y dónde todavía hace falta observabilidad y seguridad de verdad.

Mi lectura: esto es más interesante que “otro agente que codea”. Cursor está intentando meterse en el último metro del shipping: después del merge, cuando aparecen las regresiones y los riesgos reales.

1. Qué es Rollouts

Rollouts conecta el cambio de código con lo que ocurre después. Lee el PR, genera un plan de monitoreo y usa señales de deployment/telemetría para clasificar el rollout como saludable, regresión o inconcluso.

Lee el diff

Entiende qué cambió y qué debería observarse.

Arma el plan

Define logs, métricas o traces relevantes para ese cambio.

Sigue el deploy

Relaciona staging/production con señales reales.

Ayuda a reaccionar

Ante una regresión puede sugerir un revert PR o pasar el problema a un cloud agent.

2. Qué es Security Review

Es un revisor centrado en vulnerabilidades explotables, no en “estilo de código”. Busca categorías como inyección SQL/command, auth bypass, SSRF/redirects, secrets, deserialización insegura y dependencias vulnerables.

4. Cómo lo probaría yo

  1. Repo chico o servicio no crítico.
  2. Conectar source control + deploy + una sola fuente de telemetría.
  3. Elegir 5 PRs reales con distinto riesgo.
  4. Comparar qué señales eligió Rollouts vs las que hubiera elegido el equipo.
  5. Ver falsos positivos/negativos de Security Review.
  6. No permitir rollback/merge automático.

5. Caso real de prueba

PR: cambia validación de pagos.
Esperado:
- no aumenta error rate del endpoint,
- no sube latencia p95,
- no aumenta el ratio de pagos rechazados,
- no aparecen excepciones nuevas.
Si hay regresión:
- explicar cambio sospechoso,
- mostrar evidencia,
- proponer revert PR,
- NO ejecutar el merge sin revisión humana.

6. Lo que yo mediría

MétricaPor qué importa
Tiempo hasta detectar regresiónSi reduce minutos/horas reales de debugging.
Precisión de la causa sugeridaEvitar que solo “detecte humo”.
Falsos positivos de seguridadSi grita por todo, el equipo lo ignora.
PRs donde encontró algo que el equipo no vioValor incremental real.

7. Cuándo NO confiaría solo en esto

  • Compliance o auditorías formales.
  • Sistemas críticos donde una vulnerabilidad es catastrófica.
  • Repos sin tests ni telemetría útil.
  • Deployments donde “healthy” depende de negocio y no solo de infraestructura.

8. Mi checklist antes de activarlo

  • Observabilidad ya funcionando.
  • Owners de cada servicio definidos.
  • Rollback manual claro.
  • Alertas con severidad y deduplicación.
  • PR templates con contexto suficiente.
  • Reglas para secrets y PII.
  • Sin acciones irreversibles automáticas al inicio.

9. Prompt / instrucción operativa que usaría

Revisá este rollout priorizando impacto de usuario.
No concluyas "healthy" solo porque no hay errores 5xx.
Buscá:
- error rate,
- latencia,
- métricas de negocio asociadas,
- cambios en logs,
- anomalías nuevas.
Si sospechás regresión:
1. mostrà evidencia,
2. indicá el cambio más probable,
3. sugerí próximos pasos,
4. NO ejecutes rollback ni merge automáticamente.

10. Mi recomendación

Yo lo probaría si ya tenés CI/CD y telemetría. Si todavía no tenés buenas métricas, Rollouts no te arregla la observabilidad: solo automatiza la lectura de señales que ya existen.
